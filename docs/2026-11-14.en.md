# Maintenance report — 2026-11-14

[Русский](2026-11-14.ru.md)

## Scope and method

One retail GL-MT5000, experimental OpenWrt SNAPSHOT `r0-1713e8b`, Linux `6.18.60`, fw4/nftables. Maintenance used key-authenticated local SSH. Identity and versions were read from the running device before changes. Logs were located and inspected rather than assumed to be available.

Before changes, a verified OpenWrt configuration archive, a separate StealthSurf data/settings archive, the installed application files and diagnostic logs were saved privately. Before system-package changes, affected old/new file paths, package-manager metadata and configuration were backed up. An independent recovery shell and timed rollback were prepared. Recovery archives were read and checked; an actual rollback was not needed or exercised.

## System health

- Approximately six days of device and PPPoE uptime at the start.
- Low observed load; roughly 690–735 MiB available RAM across the main samples.
- Approximately 6.2–6.3 GiB free writable storage, with about 15% used after maintenance; temperature about 55–56 °C.
- Connection tracking was far below its configured capacity.
- No OOM, kernel panic or filesystem I/O error was found in the inspected boot and system logs. This is limited to retained logs, not a hardware endurance test.
- Small cumulative Ethernet error/drop counters existed. Their presence is recorded; they do not establish a new fault or explain an application problem by themselves.

## StealthSurf updater failure

The installed and successfully started version was `1.0.101`; the official router feed advertised `1.0.106`. Retained logs showed repeated scheduled attempts, application stops and watchdog recoveries, commonly about fifteen minutes apart during the overnight maintenance window. The installer log was empty and the installed executable stayed at the earlier version.

The cached ARM64/OpenWrt archive matched the SHA-256 published over HTTPS in the official feed. Required `ip-full`, nft TPROXY and NFQUEUE modules were already installed for the running kernel. Memory, temporary storage and flash capacity were sufficient.

The official package installer was invoked manually from an SSH-launched process outside the StealthSurf service. It finished with exit status zero, startup recorded `1.0.106`, the panel returned HTTP 200 and the VPN connected. Direct and VPN HTTPS probes returned HTTP 204. Router settings, six device exclusions and the device-specific route were preserved. No provider-account settings were edited.

**Unconfirmed explanation:** the updater process may have been terminated while stopping its own service. Service/process-group context and success of an external invocation are consistent with that explanation, but do not prove it. No controlled reproduction or upstream fix was established. Successful manual installation does not prove future automatic updates work.

Official sources: [router documentation](https://stealthsurf.net/routers), [installer](https://cdn.stealthsurf.net/app/router/openwrt.sh), [current feed](https://cdn.stealthsurf.io/app/router/latest.json). The feed is mutable; the tested version above is fixed historical information.

## System package changes

Twenty-six packages were updated in nine transactions: LuCI base/translation, the remaining LuCI modules, uhttpd, BusyBox, filesystem tools, PPP/PPPoE, firewall4, procd components and boot-environment/image-verification utilities. See [exact versions](packages-2026-11-14.md).

Transactions used the configured official snapshot repositories. All seven cached repository indexes verified successfully. Installing by package name retained index-based trust; no trust bypass was used. The distinction between unsigned individual APK files and a signed repository index is explained in [OpenWrt's package-signing change](https://lists.infradead.org/pipermail/lede-commits/2025-October/027374.html) and [index-trust implementation](https://lists.infradead.org/pipermail/lede-commits/2024-August/022080.html).

Each group was simulated and checked for unexpected dependency changes, then installed under a rollback timer. After each group, SSH, the authenticated LuCI entry point, the StealthSurf panel, direct HTTPS, VPN HTTPS and WAN state were checked. LuCI's HTTP 403 included `x-luci-login-required: yes` and the expected username/password form; it was the login page, not a runtime error.

The firewall update adjusted the default DHCPv6 input rule by adding the link-local destination range and changed comments. This difference was reviewed. `fw4 check` passed and a firewall reload preserved the VPN rules and connectivity.

`base-files=1~1713e8b`, the exact kernel build and libc remained pinned. The remaining advertised base-files update was not forced. This is not a blanket recommendation to run package upgrades on arbitrary snapshots.

Before reboot, PID 1 and the PPP daemon still referenced their previous executable files, illustrating why hot checks alone were insufficient. At the owner's request, one router reboot was then performed. A changed boot identifier and fresh uptime confirmed a new boot. SSH returned; PID 1 referenced the current procd executable; PPPoE established a fresh session; StealthSurf 1.0.106 connected automatically. Direct HTTPS and VPN HTTPS returned 204 and the application panel returned 200. This verifies one warm reboot and one fresh PPP connection, not recovery from a power failure.

## Logs and open issues

System logging and a local ten-minute application-log archiver were present. The application archive was around 25 MiB, below its 128 MiB policy; no archive exceeded the configured 31-day age window. Logs were relevant to the updater incident, so none were deleted. Active logs were not truncated or removed.

The former Xray debug log was close to 8 MiB and had stopped growing. After the update/restart the new log grew normally and a fresh compressed archive could be read. A `Bad file descriptor` error while rotating the old core log was observed again during the application restart. The error and possible log-size limit remain unresolved.

Intermittent provider-console timeouts and HTTP 502/503 responses appeared in retained history, followed by recovery. These were not treated as proof of router hardware failure.

## Limits

The report covers checks on one device and short connectivity probes. It does not certify streaming, mobile applications, unattended future updates, failover, long-term stability after the package changes, cold boot after a power cycle, recovery from power loss, 2.5 Gbit/s throughput, IPv6 or LAN-to-LAN switching. See the [test matrix](test-matrix.md).

## BusyBox alternatives regression found during verification

After the BusyBox update, `/sbin/ip` pointed to BusyBox instead of the still-installed full iproute2 executable. `ip -s link` no longer worked. An existing VPN session continuing to pass traffic did not catch this regression.

The package-declared alternatives were reapplied using OpenWrt's `update_alternatives install` function from `/lib/functions.sh` for the installed packages with alternatives metadata. This restored `ip-full`, the ubus log reader and the declared SSH/module-loader/download helpers without reinstalling or bypassing package trust. `ip -V`, `ip -s link`, a new system-log marker, WAN state and VPN HTTPS were checked afterwards. The finding is specific to this observed upgrade; its upstream scope is not established.
